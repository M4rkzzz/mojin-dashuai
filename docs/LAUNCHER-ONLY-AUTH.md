# 四服统一端入服认证方案

日期：2026-09-06。状态：实现和发布准备进行中，尚未启用生产拦截；最终状态以 `packs/release-1.0.0-preparation.json` 为准。

用户要求四服只允许通过统一端进入，已授权短暂重启四服。上线时间由用户推迟到 2026-09-06 北京时间 15:30；届时按已完成的真实连接检查逐服上线，未准备好的目标保持服务。

## 选定方案

复用现有 Hub API 和 PostgreSQL，增加**每次连接使用的一次性入服票据**。统一端登录后领取票据，轻量客户端组件随连接提交；游戏服务端在处理登录、加载玩家数据之前核验。通过后继续原来的 Forge/Cleanroom 登录流程。

服务端每次入服只增加一次到内网账号服务的异步请求；游戏过程中没有认证心跳、文件扫描、全量模组校验或逐 tick 联网。无需新建 Redis、外置 Minecraft 代理、皮肤认证站或公网认证端口。河北与宿迁两条游戏线路保持原样。

这个方案能阻挡普通 PCL、独立客户端，以及只复制整合包而未取得有效票据的连接。它不能证明玩家电脑上运行的是未经修改的官方程序：有合法账号的人仍可能自行实现公开协议。静态启动器标识、模组名称或写在客户端里的共享密钥都不能解决这个边界。本次做账号授权和连接凭据校验，不宣称反作弊或不可仿冒的程序认证。

## 一次连接的流程

1. 游戏完成本地加载，用户实际连接某个服务器时，客户端认证组件通过本机 IPC 向统一端申请入服。首次自动连接、手动重连、切换线路都走同一流程。
2. 统一端确认这个游戏进程、实例和启动账号，使用有效账号会话调用 HTTPS `POST /v1/join/tickets`。服务端决定角色名及身份，不接受客户端随意指定的角色名或 UUID。
3. API 返回 32 字节安全随机票据，Base64URL 后为 43 字符，120 秒有效，只对应一个账号和一个服。数据库只保存票据哈希。
4. 客户端随本次 Minecraft 连接提交票据。服务端认证组件先拦住登录包，向内部 `POST /internal/v1/join/redeem` 提交票据和此次登录名。
5. API 校验服务端身份、目标服、有效期、账号状态和精确登录名，原子消费票据，返回已核实的角色身份。重复消费、跨服使用、大小写不符均失败。
6. 游戏服确认连接仍存活且身份匹配后，放行原来的登录流程。缺少票据或校验失败就在进入世界前断开，显示具体原因。

票据在实际连接时获取，不在启动 Java 前获取，避免大型整合包加载几分钟后票据过期。失败重试领取新票据，不能复用已经消费的票据。

## 身份与旧存档

四服保留 `online-mode=false`，不切换为微软在线 UUID，也不重命名、复制、迁移玩家数据。以现有精确角色名及服务端实际使用的 UUID 为准；离线 UUID 按 `OfflinePlayer:<精确角色名>` 的既有规则保持一致。切换前核对现有身份映射，不拿客户端传来的 UUID 替换它。

| 登录方式 | 可信身份来源 | 处理方式 |
| --- | --- | --- |
| 群服账号 | 现有 Hub 会话、数据库绑定的 GameName | 校验会话有效、账号未禁用，再签发对应角色票据；“离线登录”仍可使用，但入服必须在线认证 |
| 微软账号 | 服务端向 Minecraft 官方验证得到的 Java 版资料和所有权 | 新增微软身份交换接口；不能把桌面端报告的名字当成已认证身份 |
| LittleSkin 等皮肤来源 | 仅用于外观 | 不参与账号授权，不改变名字、UUID 或存档 |

当前微软登录只发生在桌面端，没有 Hub 账号会话。因此需要 `POST /v1/auth/minecraft/exchange`：统一端经现有 HTTPS 入口提交 Minecraft access token，API 仅向固定官方资料/所有权端点验证，返回短期 Hub 入服授权（10 分钟，内存保存，到期重新交换）。不提交微软密码、OAuth refresh token；请求体和凭据不得进入网关日志、诊断包或数据库。

增加统一角色身份映射：提供方的稳定 ID → 已确认的精确角色名及游戏 UUID。已有群服账号直接沿用现有绑定；微软按官方资料建立映射。名称唯一性、受保护历史名字和大小写冲突继续检查。跨登录方式同名、官方改名撞上旧角色等情况，必须完成账号关联或管理员核实，不能按“同名就是同一人”自动合并。已有角色绑定不会因为另一种登录方式先来注册而被覆盖。

### 接入点

初版采用握手主机字段中的短扩展传递票据，在发包和收包边界增加认证适配，不改变 DNS 解析地址、服务器列表、实际连接端口。扩展只含版本标记和一次性票据；接收方提取后立即还原原主机字段，保留已有 Forge/FML 标记的原有顺序与含义。登录包在认证完成前暂不交给原处理器。

各版字段的长度和 Forge/FML 标记解析必须按实际固定版本检查，不能盲目在字符串末尾拼接。旧版 255 字符上限必须纳入长度检查；超限明确拒绝并提示，不截断地址。适配无法在原登录处理前可靠拦截时，不可退化成进入世界后踢人；先修接入点再开放强制认证。

这部分是待实现和验证的设计，尚未声称三种网络实现兼容性已通过。现有自动连接延迟修复继续保留，不能恢复旧版 `--server` 的过早连接行为。

### 本机凭据管理

- 统一端为每个游戏进程创建独立 IPC 通道，绑定启动账号、实例和进程生命周期。使用 Windows 命名管道及当前用户 ACL；随机管道标识、连接进程核对，防止误用其他实例的授权。
- 登录凭据仅由原生统一端持有，不进入网页前端、Java 参数、服务器列表、模组配置、皮肤请求或下载 URL。
- Java 只取得一次性入服票据。IPC 和网络请求在工作线程执行，界面明确显示“正在验证入服资格”。
- 游戏运行期间统一端关闭窗口转为托盘，维持必要的认证服务；真正退出统一端后，已在线游戏不中断，再次重连提示重新打开统一端。
- 切换统一端账号不能悄悄改变已经运行的游戏身份；旧进程继续绑定原账号，退出原账号或撤销授权后，后续重连需重新启动对应账号的游戏。
- 同一用户控制的恶意程序不属于 IPC 能完全隔离的范围，不把本机 ACL 宣称为程序真实性证明。

## 服务端接口与轻量实现

`join/tickets` 只接受已验证的群服或微软入服授权以及实例 ID；签发响应 `ticket / expiresAt`。使用 `Cache-Control: no-store`，不允许凭据放查询参数，不跟随重定向。

`internal/v1/join/redeem` 只在内部监听开放。每个游戏服有独立的服务凭据，API 根据凭据决定这个调用方允许核验哪个实例，不相信请求体自称的服务器 ID。内部凭据只部署于 API 和对应游戏服，不进入玩家分发包、Git 或公开下载目录。跨主机访问必须使用 TLS/受控加密隧道，不能因为“在局域网”就明文携带凭据。

票据表保存 `TokenHash / PrincipalId / InstanceId / ExactName / GameUuid / ExpiresAt / ConsumedAt`。在单次数据库事务内检查授权并将未消费的票据改为已消费，返回身份；并发两次兑换只允许一次成功。名称及实例不匹配不返回身份。过期票据由 API 后台任务定期清理，无需游戏服任务或新增缓存服务。

游戏服登录状态限定为 `待认证 → 核验中 → 已认证`，其余转为关闭；普通状态查询继续放行。不能通过重发握手、重复登录包、伪装原版客户端或直连后端绕过。所有游戏入口最终都由实际后端的同一认证组件拦截，FRP 不是认证边界。

默认总等待 20 秒、异步 HTTP 8 秒超时；单连接最多持有必要的握手与登录数据（8 KiB），异常/多余数据及时断开。每服同时核验上限 32，API 做账号级和服务凭据级限流，队列有界。FRP 可能让玩家共用来源 IP，因此 IP 不能作为身份依据，也不能使用会把整条线路封死的低阈值限流。

预计每次连接增加一趟玩家到统一 API 的 HTTPS 请求、一趟游戏服到内部 API 的请求，以及少量数据；这是设计成本，不是已经实测的耗时。微软授权交换一般在统一端登录后预先完成，过期时才刷新。游戏主线程与 Netty 事件线程均不得同步等待数据库/HTTP；完成后回到连接所属线程继续登录。

## 失败行为与边界

| 情况 | 玩家提示与行为 |
| --- | --- |
| 无票据 / 未装组件 | 请使用魔金大帅统一客户端启动本服务器，并显示下载页地址 |
| 启动器或认证组件过旧 | 请更新统一客户端及对应服务器客户端 |
| 票据失效 / 已使用 | 入服凭据已失效，请重新连接；统一端可自动重新申请一次 |
| 登录账号失效 | 请回统一端重新登录 |
| 角色不符 / 账号冲突 | 显示角色身份不匹配或需联系管理员，不自动切换成新角色 |
| 账号服务不可达 | 入服认证暂不可用，请稍后重试；已在线玩家不受影响 |

认证服务异常时不自动放行，否则关闭 API 就能绕过拦截。日志只记录实例、阶段、错误码、耗时和随机诊断编号；票据、会话、内部服务凭据以及附加票据的完整握手主机字段全部脱敏。

一次性票据防止已消费票据重放，但 Minecraft 离线模式本身不为整个游戏连接提供抗窃听保证。抓取并抢先使用未消费票据或实时转发连接是额外威胁；不要将本方案描述成抵御主动中间人的安全传输，也不将它作为反作弊。若后续要求这种威胁模型，需要另行加入经过验证的加密与连接绑定方案。

## 落地顺序与最少验收

1. 本地实现票据接口、微软身份交换、IPC、三套版本适配和拒绝提示；补充角色关联运维命令。保持生产服不拦截。
2. 做核心认证检查：票据只消费一次、过期/跨服/改名失败、未验证微软身份不能领票、脱敏与请求超时有效。一次 .NET/Java 互通检查，无需重新下载整套客户端。
3. 发布支持认证的新统一端；四服只分发新增认证组件等变更，现有差异更新渠道继续使用。仅升级统一端或仅升级整合包都不足以完成这次改造。
4. 用户通知切换后，备份目标配置与对应 JAR，先核对身份映射和内部 API 连通，逐服部署并短暂重启。只操作四个游戏进程和必要的 Hub 服务，不重启整个管理面板或无关容器。
5. 每服做一次统一端正常入服和一次普通独立客户端被拒；整组覆盖群服及微软两种登录，并核对原角色 UUID。额外做一次有效票据跨连接重复使用被拒，以及一次认证服务错误不会放行。认证单测不重复铺成每服全排列。
6. 通过后启用该服 `enforce`，记录实例、时间、版本、结果；四服都完成才报告全部切换。未经用户通知不提前改变可入服范围。

服务端配置提供 `observe/enforce/off`，生产初始保留原行为。进入 `enforce` 后不能因为请求失败自动回到 `off`。管理员本地命令可以明确关闭拦截以回滚，无需恢复世界存档；若组件本身影响启动，则恢复原 JAR 配置并重启该服。回滚会暂时恢复旧客户端可入服，必须明确记录。

## 实现清单

- `src/Hub.Api`：入服授权、微软验证、身份关联、票据表、内部兑换接口及后台清理。
- `src/Launcher.Desktop`：游戏进程绑定的认证 IPC、账号续期、托盘生命周期与错误反馈。
- `src/Launcher.Core/GameLauncher.cs`：为实例准备认证组件，建立进程授权；不改变现有身份和内存参数。
- `src/GameIntegration`：共享的票据传递约定和三个加载器适配，服务端登录前拦截及有界异步核验。
- `tools`、`deploy`、`packs`：内部凭据部署、分服模式开关、增量包、版本要求、必要验收记录。

本文件是执行方案，不是部署完成记录。用户尚未指定切换时刻，未创建定时任务。
